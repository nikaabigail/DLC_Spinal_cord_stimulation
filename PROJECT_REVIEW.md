# Обзор проекта DLC_OBS_Spinal_cord_stimulation

_Дата обзора: 2026-06-09. Просмотрен код, конфиги, git-состояние, runtime-логи и benchmark-данные. Сам DLC-проект (`C:\dlc\project\...`) и видео (`C:\dlc\videos\...`) вне примонтированных папок — выводы о них сделаны по конфигам и логам._

## 1. Что это за система

Это **closed-loop система стимуляции спинного мозга, управляемая походкой**. Крыса идёт по прозрачной беговой дорожке (подсветка снизу), сбоку снимают USB3-камеры Daheng/Galaxy кадром **1920×220 @ 100 Гц**. Поток идёт в DLCLive/PyTorch, который оценивает позу задней конечности. По углу конечности принимается решение о стимуляции.

Полный контур:

```
Galaxy-камера(ы) 1920×220@100Hz
  → DLCLive / PyTorch инференс (модель r_tm_side, 15 точек, ResNet-50, snapshot-best-380)
  → 6 точек задней конечности [hip/ankle/toes × left/right]
  → UDP binary-пакет "DDLP" на 127.0.0.1:47000
  → C++ плагин Open Ephys "Dual DLCLive Bridge" (отдельный репозиторий C:\tmp\Dual_DLC_live_plugin)
       → фильтрация точек, проверка триплета, расчёт hind angle
       → порог угла + refractory → TTL-слово
  → Open Ephys event channel → процессор стимуляции
```

**Ключевой архитектурный принцип:** Python делает только зрение и передачу точек. Решение о стимуляции (валидность триплета, угол, порог, refractory, TTL) принимает C++ плагин. Это сделано ради минимальной задержки (режим `DUAL_FAST_POSE_ONLY`).

Железо/окружение (из логов): RTX 5070 Laptop GPU, torch 2.10.0+cu128, Python 3.10.11 в `dlc_live_env`. Папка `C:\dlc_live_env` — это venv (не исходники).

## 2. Две линии кода: legacy и текущая

В репозитории сосуществуют **две разные реализации realtime**, и это главный источник путаницы.

**Legacy-линия (Stage 1–2, заменена):**
- `rt_dlc_obs.py` (1223 стр.) — кастомный realtime-контур: ROI-crop, worker-поток инференса, display-буфер с матчингом по `frame_id`, online-фильтр (pcutoff/despike/hold/median), buffer-диагностика, расчёт угла, запись видео. Конфиг — `config_rt_dlc.py`.
- `dual_rt_dlc_obs.py` (394 стр.) — двухкамерный вариант legacy с авто-выбором стороны и экстраполяцией.
- `rt_dlc_config_gui.py` (216 стр.) — Tkinter-настройщик, запускает **legacy** `rt_dlc_obs.main()`.
- `check_online_buffering.py` — симулятор/анализатор буферизации для legacy.

По `HISTORY_DLC_LIVE.md` от legacy-контура **намеренно ушли**: высокая задержка, нестабильный infer FPS, попытка лечить буферизацией только ухудшила latency.

**Текущая production-линия (Stage 7–8, DLCLive):**
- `rt_dlc_live.py` (1285 стр.) — DLCLive single-camera runtime + полноценный `GalaxyCameraSource` (Daheng SDK, low-latency NEWEST_ONLY, drain старых кадров). Конфиг — `config_rt_dlc_live.py`.
- `dual_rt_dlc_live.py` (1599 стр.) — **основной** двухкамерный runtime: reader-потоки на камеру, отдельный inference-поток, batch-инференс, `OpenEphysBridge` (UDP DDLP), stage-профайлер. Конфиг — `config_dual_rt_dlc_live.py`.
- `single_rt_dlc_live_bridge.py` (367 стр.) — **то, что реально работает сейчас**: одна левая камера, переиспользует примитивы из `dual_rt_dlc_live`, шлёт тот же DDLP-пакет (левая сторона — реальные точки, правая — NaN).
- `live_profiles.py` (450) + `run_live_profile.py` (164) — система именованных профилей (`single-best`, `single-fp16`, …) и лаунчер с `--status/--stop/--replace`.
- `send_dual_dlc_bridge_test.py` (278) — синтетический UDP-тест плагина без камер.

Документация: `README_OPEN_EPHYS_BRIDGE.md` и `README_LIVE_PROFILES.md` описывают именно текущую линию.

## 3. Фактическое состояние (по логам и benchmark)

- **Рабочий режим сейчас — `run_live_profile.py single-best`:** одна левая камера `FDE22070174`, FP32+TF32, RGB без конверсии, окно включено.
- **Производительность single-best** (`single_rt_dlc_live_bridge_debug.log`, сегодня): инференс ~18–24 мс, live_fps ~35–40, cam_fps ~34–41, `result_hz` до ~37. Отрисовка окна добавляет ~5–6 мс — поэтому для финальной стимуляции рекомендуется `--no-display`.
- **Главная нерешённая проблема — низкая детекция.** В логах стабильно `raw_visible=3/6`: видна только **левая** сторона (hl_*_l: 0.7–1.0), правая почти нулевая (hl_*_r: 0.02–0.09), `avg_raw=2.91`. Причина (по `README_LIVE_PROFILES.md` и снимкам в `debug_snapshots/`): правая камера физически не наведена на дорожку. Поэтому dual-режим сейчас не используется, а правая сторона пакета заполняется NaN.
- В `dual_rt_dlc_live_benchmark.csv` `left_triplet=0/right_triplet=0` весь прогон (пустая дорожка/нет животного), межкамерный `host_dt_ms≈0` (синхронизация камер хорошая), инференс ~29–44 мс/сторону.

## 5. Находки и риски

### 5.1. Safety-critical для контура стимуляции

Эти пункты могут привести к стимуляции по неверным или устаревшим данным. Часть зависит от поведения C++ плагина, которого нет в этих папках — его нужно проверить отдельно.

- **Нет защиты от устаревшего кадра (staleness gate).** В `dual_rt_dlc_live.py` inference-поток берёт «последний кадр» каждой камеры и спаривает их по номеру последовательности; `host_dt_ms` считается, но нигде не проверяется порог. Если одна камера зависнет (USB, кабель), вторая продолжит давать новые кадры, и система будет бесконечно слать в плагин пары, где одна сторона — старый кадр (возможно, на сотни мс–секунды), с свежим `host_time`. **Нет per-side проверки возраста кадра перед `bridge.send`.** Это самая важная находка.
- **Нет watchdog/heartbeat при полном зависании.** Если обе камеры «молча» зависнут в `read()` без исключения, Python просто крутится вхолостую и перестаёт слать пакеты. Сигнала «я ослеп» нет — плагин обязан иметь собственный таймаут на вход.
- **Single-bridge не валидирует конфиг.** `dual_rt_dlc_live.main()` зовёт `validate_dual_config()`, которая в т.ч. проверяет, что `DUAL_USE_POINTS` совпадает с фиксированным binary-порядком точек. `single_rt_dlc_live_bridge.py` **не зовёт никакой валидации**. Если порядок точек когда-нибудь разойдётся, single-режим молча отправит binary-пакет с переставленными точками — плагин посчитает угол по не тем точкам, и порог стимуляции исказится. Рекомендация: вызвать `dual.validate_dual_config()` в начале single-bridge.
- **Безопасность NaN-заглушки правой стороны зависит от плагина.** Неактивная сторона — 6×3 NaN, `raw_visible=0`. Это безопасно **только если** C++ плагин проверяет валидность как `isfinite(x)&&isfinite(y)&&isfinite(l)&&l>=thr`, а не через числовой sentinel (например `x==-1`). Сравнения с NaN в IEEE-754 всегда false — при `isfinite`-проверке правые TTL-линии останутся низкими. **Это нужно подтвердить в коде плагина.**
- **FP16/TF32 могут сдвинуть момент срабатывания триггера.** Угол считается по трём точкам; субпиксельные сдвиги координат у порога могут переключать TTL иначе, чем в чистом FP32. Профили `single-fp16`/`dual-fp16` в заметках предупреждают «сравни с FP32 перед стимуляцией», но **код это никак не enforce'ит** — fp16-профиль на один CLI-токен от боевого UDP-пути. Даже рекомендованный `single-best` (FP32+**TF32 on**) не побитово равен FP32; единственный полностью воспроизводимый режим — `single-strict` (TF32 off).
- **UDP-отправка — fire-and-forget, ошибки проглатываются.** Сокет non-blocking; при переполнении буфера `sendto` бросает `BlockingIOError`, который ловится и логируется как warning — пакет теряется. Нет счётчика потерянных отправок и нет детекции, что плагин не слушает (ACK по умолчанию выключен). Стоит считать потери и периодически предупреждать.
- **Латентный `NameError` в `dual_rt_dlc_live.py`:** вызывается `print_model_device_after_init(...)`, а определена `log_model_device_after_init(...)`. Срабатывает только в sequential-ветке с processor'ом (т.е. при `DUAL_FAST_POSE_ONLY=False`), но тогда уронит inference-поток и через `last_error` остановит систему. Реальный баг, замаскированный текущим fast-конфигом.

### 5.2. Тест-харнес расходится с реальным форматом

- `send_dual_dlc_bridge_test.py` повторяет 252-байтный DDLP-формат вручную, но **никогда не шлёт NaN/None** и собирает байты независимо от боевого упаковщика. Значит safety-критичный путь «пропущенная точка → NaN», от которого зависит плагин, end-to-end не тестируется. JSON-режим теста использует `allow_nan=True`, а runtime — `allow_nan=False`; TTL-тест шлёт поля (`valid/angle_deg/picked_side`), которых боевой `_build_ttl_payload` не формирует. Тест валидирует *спецификацию*, а не *реализацию* — стоит импортировать боевые упаковщики, чтобы ловить дрейф.

### 5.3. Offline DLC-пайплайн (`run_dlc.py` и проверки)

- **`run_one_eval.py` — чужой мёртвый код.** Это не DLC, а EEGNet-скрипт (`from plot_figures.src.eval_accs import ...`), модуля нет в репозитории — `ModuleNotFoundError` при любом запуске. Удалить из проекта.
- **Пост-обработка не выстраивается в цепочку.** `filter_mild`, `interpolate_mild`, `despike_mild` все читают *сырой* `<stem><SCORER>.h5`, а не результат предыдущего шага; despike/interp пишут под ключом `df_with_missing` с суффиксами, которые `create_labeled_video(filtered=True)` не подхватывает. То есть «очищенные» треки получаются, но никуда не идут.
- **`interpolate_mild` присваивает выдуманным точкам likelihood 0.7** (`pcutoff+0.1`) — для исследовательских данных это спорно: интерполированные точки выглядят как реальные детекции выше порога.
- **Хрупкая ручная связка `SHUFFLE`/`SCORER`.** Две глобали (`run_dlc.py:16,19`), которые надо править руками после переобучения; код сам предупреждает, что они «плывут» после `create_training_dataset`. Молчаливый fallback на `scorers[0]` в одних функциях и `[WARN]` в других.
- **`finetune_from_300` грузит `snapshot-330.pt`** (имя/значение не совпадают; на текущей машине такого снапшота может не быть).
- **`PROJECT_PATH`/`CONFIG_PATH` объявлены 4 раза** в трёх файлах, везде абсолютные Windows-пути `C:\dlc\...`, без `argparse` и env-override. Запись `config.yaml` — без бэкапа, теряет комментарии.

### 5.4. GUI и лаунчер

- **`rt_dlc_config_gui.py` настраивает legacy-пайплайн** (`rt_dlc_obs`), а не текущий DLCLive. Запускает `rt_dlc_obs.main()` *после* `root.destroy()` без try/except — исключение просто роняет процесс. Главный «предохранитель» (авто-cap FPS) неактивен при дефолтном `VIDEO_TARGET_FPS=0.0`, т.к. реальный FPS известен только после открытия файла.
- **`run_live_profile.py` — хрупкое управление процессом.** Нет PID-файла; «запущен ли live» определяется через PowerShell-скан процессов. Между проверкой и запуском есть TOCTOU (можно получить два процесса на одну камеру); `--replace` не дожидается освобождения камеры после kill; `Stop-Process -Force` минует `finally` runtime'а, поэтому камера/сокет не закрываются штатно → периодическое «camera busy».
- **Окно включено по умолчанию во всех профилях**, включая рекомендованный. Безопасное headless-состояние для стимуляции держится на том, что оператор не забудет `--no-display`. Профиль `single-debug` фактически дублирует `single-best` (отличается только частотой логов), хотя позиционируется как особый визуальный.

## 6. Документация vs реальность

Главное несоответствие: **корневой `README.md` и `README_DLC_live.md` описывают legacy-архитектуру** (`rt_dlc_obs.py`/DLCLive single «minimal»), а реальный production (Open Ephys bridge, профили, single/dual DLCLive) описан только в *незакоммиченных* `README_OPEN_EPHYS_BRIDGE.md` и `README_LIVE_PROFILES.md`. Новый человек, читая корневой README, начнёт не с того файла. `rt_dlc_live.py` тоже уже не «минимальный» из Stage 7 — оброс полным Galaxy SDK.

## 7. Сильные стороны

- Чёткая абстракция источников кадров (`FrameSource` → Camera/Galaxy/VideoFile), грамотный low-latency путь (NEWEST_ONLY + drain старых кадров) — для realtime это правильно.
- Богатая диагностика: stage-профайлер по стадиям (camera/read, preprocess, inference, pack/send, display), benchmark-CSV, детальные логи с likelihood по точкам.
- Разумное разделение ответственности Python (зрение) / C++ (решение о стимуляции) ради latency.
- Аккуратный online-фильтр (pcutoff/despike/hold/median) с защитой от «перезахвата» после долгой потери точки.
- Зависимости осознанно зафиксированы там, где это критично (`numpy<2`, non-headless OpenCV) — ровно те грабли, что описаны в истории.
